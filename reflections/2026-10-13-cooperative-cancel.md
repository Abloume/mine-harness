## 视角四 · 协作式取消契约

> 核心原则：取消不是强杀命令，而是一段受控的状态转换——让系统知道
> 停在哪里、留下了什么、接下来由谁负责收尾；副作用先分类再补偿，
> 不可逆动作执行前解决，最终状态如实（不把"进程已停"冒充"外部世界已恢复"）。

| 原则 | 与 mine-harness 现状的对照 | 状态 |
|---|---|---|
| **取消状态机**：running → cancel_requested → canceled / partially_completed / needs_review | 现只有软停止（StatusAborted + Reason，交还用户）；无 cancel 状态、无外部信号注入（`Run(task)` 没有 context） | 🆕 |
| **安全检查点**：步骤边界检查取消（调用工具前查一次、返回后记录结果再查一次），最多多完成一个可控单元 | 无——中止只发生在循环检测/审批/重试预算处，没有"工具调用前后检查取消"概念 | 🆕 |
| **副作用分类 + 补偿声明**：只读（直接结束）/ 可补偿（声明补偿动作）/ 不可逆（执行前解决） | 有风险分级（RiskLevel + 参数修正）拦"越权"，但无副作用类型与补偿契约 | 🆕 |
| **逆序补偿 + 补偿账本**：按执行日志逆序调用补偿；补偿本身可能失败，记录尝试次数与人工接管入口 | 无补偿机制；审批拒绝的"停止该动作"文案是雏形（拦新副作用，不撤旧副作用） | 🆕 |
| **幂等键**：外部调用带请求标识，超时后用同一键查结果而非重新创建 | 无——MCP Client 超时只是报错；run_cmd 无幂等概念（重复执行有副作用） | 🆕 |
| **不可逆动作执行前解决**：二次检查取消状态 + 不可中断区 + 高风险人工确认 | 审批点（fail-closed + 连续拒绝升级）部分对齐"人工确认"；缺"取消状态下二次检查" | 📋 |
| **状态如实**：不可逆阶段显示 partially_completed / needs_review，如实告知 | 软停止 Reason 语义对齐（交还用户、说明中止原因）；缺 partial / needs_review 分级 | 🆕 |
| **取消竞态测试**：卡在最尴尬的时刻（请求发出后响应前取消、外部成功后本地落账前取消、补偿执行一半再失败） | 评测门有对抗用例（绕过审批、循环诱导）；缺"取消竞态"用例族 | 🆕 |

## 优先级结论

1. **先补（内核级，改动集中）**
   - `Run` 接入 `context.Context`（外部取消信号）+ cancel_requested 状态机；
   - 安全检查点：工具调用前查一次、返回后记录结果再查一次；
   - 副作用契约：工具声明副作用类型（readonly / compensatable / irreversible）
     与补偿动作；任务取消时按执行日志逆序补偿。
2. **与既有机制分工**：审批拦「越权动作」，取消拦「外部指令中止」，
   循环检测/重试预算拦「自我空转」——三类护栏互不重叠、可叠加。
3. **第 8 步评测集扩充**：取消竞态用例（请求发出后响应前取消等最尴尬时刻）；
   轨迹导出记录"取消点"（停在哪个安全检查点、已补偿哪些步骤）。
